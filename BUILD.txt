This one drop contains TWO independent pieces of work. They don't depend on each
other - you can do them in either order.

================================================================================
PIECE 1 - Run the database migration 0108 (Supabase SQL editor)
================================================================================
WHAT IT DOES (no behaviour change for legitimate users):
  A. Pins search_path = public on the 17 SECURITY DEFINER functions that still
     had a mutable search_path (the other 66 already had it). Closes the
     "Function Search Path Mutable" class of issue.
  B. Locks down the 10 dev-seed functions. They were callable by anyone
     (anon/authenticated) with NO auth check, and dev_reseed_all() is
     DESTRUCTIVE (it deletes + re-seeds a patient's data). 0108 revokes their
     EXECUTE from anon/authenticated/PUBLIC and grants only service_role. Your
     /api/dev/scenario route calls them via the service-role client, so it keeps
     working; you can also still run them from the SQL editor.

HOW:
  - Open the Supabase SQL editor and run the standalone file included beside the
    zip: 0108_harden_secdef_functions.sql
    (identical to supabase/migrations/0108_harden_secdef_functions.sql).
  - It's safe to run before OR after the Next 16 deploy below.

ALREADY VERIFIED (throwaway Postgres 16, full migration replay + catalog checks):
  - 0 functions left with a mutable search_path; all 17 still execute cleanly.
  - dev functions: anon/authenticated EXECUTE = false, service_role = true.
  - a normal RPC's grants (submit_weekly_checkin_v4, set_own_sex, ...) unchanged.
  - from-scratch CI replay INCLUDING 0108 applies cleanly (CI stays green).

NOT done on purpose - FORCE ROW LEVEL SECURITY:
  Forcing RLS would break your write path: 16 of your policies are TO
  authenticated only, and the SECURITY DEFINER functions run as postgres, which
  would then have no matching policy -> silent deny. It's also not verifiable in
  the test harness. Full reasoning + a safe staged-rollout recipe are in
  docs/audits/security-definer-audit-2026-06.md (section F3).

Two follow-ups are written up in that audit (F2: tighten the broad
EXECUTE-to-PUBLIC grants; F3: staged FORCE RLS). Both need their own tested pass.
